## 3. 그대로 구현하면 깨지는 것 🔴

1. **DDL에 `IF NOT EXISTS`가 없다** (기획서 5-2, 5-3)
   - DR-016·FR-DATA-003은 "모든 문장이 멱등"을 요구한다.
   - 그런데 초안 DDL은 `CREATE TABLE`/`CREATE INDEX`만 쓴다. 그대로 `contracts/db-schema.sql`로 옮기면 두 번째 기동부터 에러가 난다.
   - 수정: 모든 문장을 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`로.

2. **SSE + JWT 조합** (FR-FE-011, IF-INT-BE-011)
   - 브라우저 `EventSource`는 GET만 지원하고 `Authorization` 헤더를 보낼 수 없다.
   - 수정: FR-FE-011에 "`POST /api/chat` 스트림은 `fetch` + ReadableStream으로 읽는다(EventSource 사용 금지)"를 명시.

3. **메일 링크 404** (FR-FE-016, FR-MAIL-005)
   - 메일 본문의 `APP_BASE_URL/incidents/{id}`로 바로 들어오면 nginx가 정적 파일을 못 찾아 404를 낸다.
   - 수정: FR-FE-016에 SPA fallback(`try_files $uri /index.html`) 추가.

4. **계획 단계가 전부 C(빨강)로 나올 위험** (FR-AG-004, FR-AG-006)
   - 티어는 `action_id`가 `actions.yaml`에 있어야 A/B가 된다. 그런데 LLM 계획 스키마에서 `action_id?`는 선택 항목이다.
   - LLM이 자기 표현으로 단계를 쓰면 미등록 → 전부 C → 데모 화면이 빨간 배지로만 채워진다.
   - 수정: FR-AG-004에 "프롬프트에 팩의 허용 동작 ID 목록을 넣고, 각 단계는 그중 하나를 `action_id`로 고르게 한다(목록에 맞는 게 없을 때만 생략)"를 추가.

## 4. 개선 제안 🟡

### 4-1. 문서 분량 — 금요일용 요약본을 따로

- 2.5일 MVP인데 요구사항이 FR 178건·NFR 82건이다. v1.2에서 추가된 FR-LT 24건, 차별점 매핑 등은 금요일 코드에 거의 영향이 없다.
- Claude Code는 문서를 많이 읽을수록 컨텍스트를 잃고 [이후] 항목에 손대기 쉽다.
- 제안:
  - 금요일 [필수]만 뽑은 2~3쪽짜리 `docs/mvp-checklist.md`를 만든다.
  - 루트 CLAUDE.md와 야간 루프는 그 파일만 기준으로 삼게 한다.
  - 원본 두 문서는 참고용으로 두고, **더 늘리지 말고 동결**한다.

### 4-2. LLM 공급자 보류가 데모를 약하게 만든다

- 공급자가 미정이면 데모 기본은 fallback 리포트다. 화면에서 원인이 "확인할 수 없음"으로 나와 핵심인 "AI가 분석한다"가 보이지 않는다.
- 멘토가 "OpenRouter를 써도 되고 기존 키를 써도 된다"고 선택지를 줬다. 데모 규모면 비용은 몇 달러 수준으로 추정된다.
- 제안: 결정 기한(10/15 12:00) 전에 키 하나라도 확정.

### 4-3. 일정 재기준

- B1 기한(10/14 21:00)이 지났고 실제 상태가 문서와 다르다.
  - 레포 `main`(프론트 코드)과 `dev`(폴더 뼈대)가 갈라져 있다.
  - `contracts/`는 README만 있다.
  - uv workspace(`pyproject.toml`)가 없다.
  - `dev`의 CLAUDE.md·`.env.example`이 PostgreSQL 기준이다(기획서는 SQLite).
- 제안: 10/15 09:00 스탠드업에서 9-2 일정을 현재 상태 기준으로 다시 맞춘다.

### 4-4. 프론트 현재 구현과 계약 스키마 차이

- `main`의 프론트는 원인 후보별 "검증 결과(확인/반증)"를 보여 준다. 이는 기획서가 [이후]로 미룬 "후보별 읽기 전용 검증"에 가깝다.
- 이 밖에도 KPI 4종, 근거 형식, 계획 단계(티어 배지·precheck 없음), 토큰 저장 위치(localStorage)가 기획서와 다르다.
- 제안: 시간상 **데이터 형식은 기획서(7장·SRS 6-2) 기준으로 맞추고, 화면 구성은 살린다.**

### 4-5. 멘토의 확장 방향 — 조건부 후순위로

- 멘토 발언: "금요일까지 구축 완료하고 추가로 어느 것을 더 할 수 있는지 논의", "이것도 볼륨이 작을 수 있어요. 진행 속도 봐서 가능하겠다 싶으면 게임 + CS 상담 + 마케팅 + 인프라로 갈 수도".
- 조건이 붙은 발언이므로 **구현 우선순위는 후순위**다. 금요일까지 이를 위한 작업은 하지 않는다. 지금의 "공통 엔진 + 도메인 팩" 구조가 이미 이 확장을 받을 수 있다.
- 다만 기획서처럼 L4(2-3: GPU·제조 팩과 같은 단계, 1-3-0: 그 뒤)로 순서를 고정하는 것은 맞지 않다. 멘토는 이를 먼 미래 비전이 아니라 "범위가 작으면 다음에 붙일 후보"로 말했고, 진행이 빠르면 L2·L3보다 먼저 하자고 할 수도 있다.
- 제안:
  - 문서 표기를 L4 고정 대신 "**조건부 확장 후보** — 필수 범위 완료 후 진행 속도에 따라 멘토와 결정"으로 바꾼다.
  - 금요일에는 "엔진은 그대로 두고 도메인 팩으로 붙이는 구조라 이런 순서로 가능하다"를 한두 문장으로 답할 수 있게만 준비한다.

### 5-3. 그대로 구현하면 깨지는 것 (3차)

1. **`actions.yaml` 예시의 B 동작에 precheck·rollback 문구가 없음** (기획서 6-3)
   - SAFE-07에 따라 B 단계는 precheck·rollback이 없으면 C로 강등된다.
   - 그런데 예시의 `restart_service`·`clean_temp_files`에는 `requires`만 있고 문구가 없다. 그대로 쓰면 LLM 없는 데모(fallback 계획)에서 B 단계가 전부 빨강 C로 나온다.
   - 반영: 두 동작에 `command_preview`·`precheck`·`rollback` 예시 문구 추가.
   - `clean_temp_files`는 v1.2의 `cleanmgr`가 되돌릴 수 없어 B 정의("가역 변경")와 맞지 않았다. 격리 폴더로 옮기는 방식으로 바꿨다.
2. **Network 유형의 fallback 규칙 공백** (기획서 4-5, SRS FR-AG-023)
   - 1차 검토로 `metrics.yaml`에 `net`을 추가했지만, `fallback_plans`에는 cpu/mem/disk만 있다.
   - 기존 규칙("분류 불가면 A 단계만")으로는 `net`처럼 분류는 되지만 목록이 없는 경우가 정의되지 않았다.
   - 반영: `fallback_plans`에 목록이 없는 유형도 A 단계만 만든다고 명시.

### 5-5. 남은 한계

- 위 확인은 **지적한 항목이 제대로 반영됐는지**와 **기계적으로 검사할 수 있는 것**에 한정된다.
- 두 문서는 합쳐 2,800줄이 넘어 내용 판단이 필요한 오류가 더 있을 수 있다.
- 각 파트 담당자가 자기 파트 절(예: Agent는 4-5·FR-AG, Backend는 7-1·FR-BE)을 읽어 보는 것이 가장 확실하다.
