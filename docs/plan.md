## 1. 개요

### 1-1. 문제

- 새벽·주말 장애 알람이 오면 당직자는 Zabbix 화면, 서버 접속, 과거 기록을 오가며 원인을 찾는다. 초동 분석에 시간이 오래 걸리고, 보고서 작성은 사람 몫이다.
- AI에게 맡기면 "모르는 값을 지어내는 문제"와 "운영 서버를 마음대로 바꾸는 문제"가 생긴다.

### 1-2. 해결 (MVP 한 줄)

> Zabbix 알람이 뜨면 AI가 **조회만으로** 원인 후보와 영향 범위를 정리하고, 바꿔야 할 것은 **계획(미리보기)으로만** 제시하며, 모든 수치에 **근거(어떤 도구로 언제 조회했는지)** 를 붙여 담당자에게 메일로 보낸다.

### 1-3. 차별점과 특색 **[v1.2 차별점 보정 — 전면 확장]**

> v1·최종본의 1-3은 3줄이었다(아래 원문 보존). v1.2에서 팀의 차별점을 **3개 축**으로 정리하고, 통합 기획서(Google Drive "Deja Fix ― 장애 대응 코파일럿 통합 기획서", 예진, 2026-10-14)의 **모든 장을 원문 수준(표·예시·수치 유지)으로 옮긴 뒤**, 각 항목이 금요일 MVP(Zabbix·SQLite·미리보기 한정·멘토 지시)에서 어떻게 구현·연결·시연되는지와 장기 로드맵에서 언제 원안대로 완성되는지를 덧붙였다. 멘토 지시와 충돌하는 원안은 지우지 않고 **"금요일 MVP에서는 ○○로 대체, 장기 범위에서 원안 구현"**으로 병기했다.
>
> (v1 원문 보존) 멘토 정의 채택: **하나의 공통 엔진 + 산업별 특화 기능 연결**. MVP의 공통 엔진 = "알람 → 조회 → 근거 있는 분석 → 미리보기 계획 → 보고" 파이프라인. IT 서버는 첫 번째 특화(`packs/it/`). 장기 차별점(통합 기획서): 실행 전 안전 심사 레이어, 영향 시뮬레이션·롤백 플랜, 평가 하네스. MVP에서는 "실행 없음 + 티어 라벨 + 근거 추적"이 그 씨앗이다.

세 축의 관계: **①은 "무엇을 어떻게 넓히는가"(제품 구조)**, **②는 "왜 우리여야 하는가"(시장 차별)**, **③은 "어떻게 믿을 수 있게 만드는가"(설계 원칙)**다. ③은 ②의 금요일판 최소 구현이고, ①은 ②·③을 산업마다 다시 만들지 않게 해 준다 — 안전 규칙(티어·롤백·근거)은 엔진에 한 번 만들고, 무엇이 위험한 동작인지는 팩(`actions.yaml`)이 산업별로 알려 준다.

#### 1-3-1. 축 ① 공통 엔진 + 도메인 팩 (DIF-1)

**정의 (팀장 → 멘토 제시안, 멘토 노션 채택)**
- 산업별로 서비스를 따로 만들지 않는다. "알람 → 조회 → 근거 있는 분석 → 미리보기 계획 → 보고"를 하는 **공통 엔진** 하나 위에, 산업마다 다른 것(감시 대상 지표의 이름, 위험한 동작 목록, 분석 프롬프트, 용어)만 **도메인 팩**으로 갈아 끼운다.
- 확장 순서: **IT 서버 장애 대응(금요일 MVP) → GPU 인프라 → 제조 설비**. 멘토 제안: **게임 + CS 상담 + 마케팅 + 인프라**를 묶은 **전사 업무 솔루션**. 프로젝트는 끝까지 **1개**(저장소 `https://github.com/DejaFix/DejaFix` 하나, 엔진 하나).
- **[v1.3] 전사 업무 확장의 위치**: 멘토 발언은 "이것도 볼륨이 작을 수 있어요. 진행 속도 봐서 가능하겠다 싶으면 …갈 수도"라는 **조건부**다. 그래서 구현 우선순위는 후순위(금요일까지 이를 위한 작업 없음)로 두되, L4처럼 순서를 고정하지 않는 **조건부 확장 후보**로 분류한다. 필수 범위가 끝난 뒤 멘토와 착수 시점을 정하며, 진행이 빠르면 L2·L3보다 먼저 할 수도 있다. 지금의 엔진·팩 분리 구조가 이 확장을 받는 준비다.
- Graphio(장재현) 기획서의 같은 개념: "공통 코어 + YAML 도메인 팩", "분야가 바뀌면 지도와 도메인 팩만 교체", IT → AI 인프라 → 제조 → 유통·물류 → AX 플랫폼.
- 통합 기획서의 확장 비전과도 겹친다: "장애 대응은 첫 적용 사례이고, 안전 심사 구조는 모든 업무 에이전트의 실행 안전 심사로 확장할 수 있다." 즉 축 ②의 안전 레이어가 엔진에 있고, 팩이 늘어날수록 같은 안전 레이어를 재사용한다.

|---|---|---|

**금요일 MVP에서의 씨앗과 증명 방법**
1. **폴더 분리**: `packs/it/actions.yaml`·`metrics.yaml`·`prompts/`가 엔진(`agent/`, `backend/`, `scheduler/`, `mcp-zabbix/`)과 분리되어 있다(DR-021, F18 후속 작업).
2. **하드코딩 금지 규칙**: 엔진 코드에는 `system.cpu.util`, `vfs.fs.size[...]`, `restart_service` 같은 IT 전용 아이템 키·동작 ID·문구를 쓰지 않고 팩에서 로드한다 → 요구사항 **NFR-EXT-001(필수)**, 검증은 `rg`로 엔진 폴더 검색 0건(테스트 fixture 제외).
3. **팩 경로 한 곳**: 활성 팩은 설정 한 곳(변수 이름 (TODO: 추후결정 — 후보: `DOMAIN_PACK`), 값 `it` — 요구사항 NFR-EXT-002·AS-B12)에서만 정한다.
4. **팩만 바꾸면 결과가 바뀐다는 증명(데모 장면 D-ENGINE, 11-5)**: 발표 중 `packs/it/actions.yaml`을 화면에 띄워 "CPU 장애의 계획 단계와 티어는 이 YAML이 정한다, GPU 팩은 이 폴더 하나를 추가하는 것"이라고 설명한다. 여유가 있으면(선택) 리허설에서 `restart_service`의 티어를 바꾼 YAML로 재기동해 같은 장애의 배지가 바뀌는 것을 녹화해 둔다.
5. **두 번째 팩 실증은 금요일 이후**: `packs/gpu/` 시험 팩을 YAML만 추가해 엔진 코드 변경 없이 E2E 1회 → NFR-EXT-004(이후).

#### 1-3-2. 축 ② 실행 전 안전 레이어 (DIF-2) — 통합 기획서 원문 전체 + MVP 연결

이 절은 통합 기획서의 장 순서를 그대로 따른다. 각 장의 **원문**(표·예시·수치 유지) 뒤에 **"DejaFix 금요일 MVP에서는"** 단락으로 구현·연결·시연을 붙였다.

##### (1) 개요와 포지셔닝 — 원문

장애 대응 코파일럿은 알람부터 보고까지 7단계를 처리하되, 핵심 가치는 **"AI 에이전트가 조치를 실행해도 괜찮은지를 실행 전에 판단하고, 그 안전성을 숫자로 증명하는 안전 레이어"**에 둔다.

- **한 줄 포지셔닝:** 기존 제품은 원인을 찾고 조치를 추천한다. 우리는 그 조치가 일으킬 영향을 실행 전에 계산하고, 안전성을 고객 환경에서 직접 측정한다.
- **주 고객:** 망분리 규제로 글로벌 SaaS를 쓰기 어려운 국내 금융·공공 운영팀 (B2B)
- **확장 비전:** 장애 대응은 첫 적용 사례이고, 안전 심사 구조는 모든 업무 에이전트의 실행 안전 심사로 확장할 수 있다.
- **통합 범위:** 이태윤 PRD(Graphio for AIOps), 장재현 AI 인프라 장애 대응 시스템 기획서, 김준하 경쟁분석 문서, 핵심 차별점 문서를 하나로 합쳤다. PRD와 기획서 본문은 열람 권한이 없어 슬랙에 올라온 요약을 기준으로 반영했다.

**DejaFix 금요일 MVP에서는**
- 포지셔닝 문장은 **발표 첫 슬라이드에 그대로** 쓴다. 다만 금요일 데모가 증명하는 범위는 "실행 전에 **멈추는** 구조(실행 경로 없음 + 코드가 정하는 티어 + 근거 없는 값 차단)"까지이고, "영향을 **계산**"과 "고객 환경 **실측**"은 L3 로드맵으로 말한다(과장 금지 — 아래 (4) "주장하면 안 되는 것"과 같은 원칙).
- 주 고객: 망분리 금융·공공은 **(TODO: 추후결정 — 후보: 국내 금융·공공 운영팀(통합 기획서 가설), 사내 IT 당직 운영팀)**. 금요일 데모 페르소나는 "사내 IT 서버를 혼자 맡은 당직 운영자"(1-4 [결정]). 망분리 고객과의 연결 고리는 이미 설계에 있다: LLM을 `LLM_BASE_URL` 하나로 사내 게이트웨이로 바꿀 수 있고(4-6, NFR-MAINT-006), LLM 없이도 fallback 리포트·계획으로 흐름이 끝까지 돈다(D-05) — "외부 LLM을 못 쓰는 망에서도 최소 기능은 동작"이라는 시연 메시지가 된다.
- 확장 비전은 축 ①과 합쳐 "엔진의 안전 레이어를 팩마다 재사용"으로 설명한다.

##### (2) 문서 간 충돌과 통합 판단 — 원문 12개 표 + DejaFix 처리

네 문서가 서로 다르게 말하는 항목은 12개이고, 팀 결정이 필요한 핵심 충돌 6개와 숫자·범위만 다른 충돌 6개로 나눴다. 본문은 "통합본 채택" 열을 기준으로 작성했고, PRD와 기획서는 슬랙 요약 기준이라 본문과 다를 수 있다. 오른쪽 열은 v1.2에서 붙인 DejaFix(멘토 지시 우선) 처리다.

##### (3) 문제 정의와 목표 지표 — 원문 + MVP 연결

AI 에이전트가 운영 명령을 대신 실행하는 것이 늘고 있지만, 승인자는 여전히 명령어 한 줄만 보고 판단한다.

- **조치가 장애를 키운다:** 2017년 AWS S3 장애는 서버 일부를 제거하려는 명령의 입력 실수로 의도보다 많은 서버가 제거돼 발생했고, 2021년 Facebook 장애는 유지보수 명령이 백본을 끊었는데 이를 막을 감사 도구에 버그가 있었다.
- **정확도를 검증할 수 없다:** 벤더가 제시하는 수치만 있고, 고객이 자기 환경에서 AI의 정확도를 측정할 방법이 부족하다.
- **국내 환경에 맞지 않는다:** 글로벌 SaaS 중심이라 폐쇄망·망분리와 한국어 운영 문서에 약하다.

|---|---|---|---|---|
| 원인 TOP3 적중률 | 80% 이상 | 정답 라벨(주입한 장애의 실제 원인) 필요 | 주입 시나리오는 정답을 안다(CPU 부하 = `inject-cpu.ps1` 프로세스). 리허설마다 리포트 원인 후보에 정답이 있는지 수동 기록(NFR-EVAL-002, 선택). fallback 리포트는 원인을 "확인할 수 없음"으로 두므로 적중률 대상에서 제외하고 따로 센다 | 하네스 자동 채점(NFR-EVAL-003) |

##### (7) 에이전트 구성 — 원문 + 단일 AI Agent로의 대응

장애 대응 흐름은 분석·검증·조치·보고·평가 에이전트가 맡고, 조치 직전에 안전 심사 오케스트레이션이 끼어든다(원문).

| 에이전트 (원문) | 역할 (원문) | DejaFix 금요일 MVP에서는 (AI Agent **1개**의 상태·모듈로 대응 — 멘토 구조도) |
|---|---|---|
| 오케스트레이터 | 호출 순서·상태 관리, 안전 심사 결과가 차단이면 조치 중단 | 상태 머신 QUEUED→COLLECTING→ANALYZING→VALIDATING→REPORTED→PLANNING→DONE(4-5). "차단이면 중단"은 해당 없음(실행 없음) |
| 분석 | 로그·메트릭·배포 이력·온톨로지로 원인 가설 생성, 영향 범위 요약 | COLLECTING(고정 수집 세트) + ANALYZING(LLM 1회, 미설정 시 fallback) |
| 검증 | 가설별 읽기 전용 명령으로 확인/반증, 원인 TOP3 재순위 | VALIDATING은 **근거 검증**(SAFE-08)이지 가설 검증이 아니다. 가설 검증 루프는 선택(FR-AG-018) → 이후(FR-LT-011) |
| 안전 심사 (6종) | 영향 범위, 용량·SLO, 정책·시간, 롤백 가능성, 신뢰 이력, 반대 심문. 근거만 제출 | PLANNING의 규칙 한 겹(티어 강제·롤백 필수)이 "롤백 가능성" 관점 하나에 해당. 나머지 5관점은 이후(FR-LT-004) |
| 조치 | 승인된 명령 실행, 결과·종료 코드 수집 | **없음**(멘토 구조도: 변경은 계획까지). L3 |
| 사후 검증 | 예측과 실제 지표 비교, 다르면 롤백 제안 | 없음. L3 |
| 보고 | JIRA 티켓, 조치 보고서, 담당자 메일, 사후 분석 | 리포트 저장(Agent) + 메일(Backend 메일 워커, D-03) |
| 평가 | 장애 리플레이·카오스 시나리오로 성능·안전성 상시 측정 | 사람이 하는 리허설 측정 + pytest 안전 회귀 세트 |

*[다이어그램 — 원문은 그림] 안전 심사 오케스트레이션: 심사 6종 → 규칙 엔진 → 4단계 결정*

```
 [조치 후보] ─► 오케스트레이터 ─┬─► 영향 범위 심사 ─┐
                               ├─► 용량·SLO 심사 ──┤
                               ├─► 정책·시간 심사 ─┤   구조화된 근거만 제출
                               ├─► 롤백 가능성 심사 ┼──────────────► 규칙 엔진(정책 코드) ─► 자동 실행 / 1인 승인 / 2인 승인 / 차단
                               ├─► 신뢰 이력 심사 ─┤        ▲
                               └─► 반대 심문 ──────┘        │ 새 위험 발견 시 해당 관점 재호출
                                                   └────────┘
 금요일 MVP: [계획 단계] ─► actions.yaml 매칭(코드) ─► 롤백 없는 B는 C 강등 ─► 배지 A/B/C (실행 없음)
```

에이전트끼리 투표하면 비슷한 모델이라 같은 실수를 함께 할 수 있어, 심사 에이전트는 구조화된 근거만 내고 결정은 규칙 엔진이 한다. 반대 심문이 새 위험을 찾으면 오케스트레이터가 해당 관점을 다시 호출한다. (경쟁분석 문서의 "안전 심사 에이전트 1개가 거부 시 차단" 구조와는 다르다 — 원문)
→ **금요일 MVP와의 일치점**: "LLM은 결정하지 않는다"는 원칙은 금요일부터 그대로다. LLM이 계획 JSON에 `tier:'A'`라고 적어도 코드가 `actions.yaml` 기준으로 덮어쓴다(FR-AG-006 수용 기준: LLM이 A라 적은 `reboot_host` → C).

| 노드·인프라 | 디스크 가득 참 | 로그·이미지 정리 | 필요한 파일·이미지까지 삭제 | 예비 시나리오(선택): `clean_temp_files`(B, 롤백 필수) vs `delete_recursive`(C) |
| 노드·인프라 | 메모리·CPU 고갈, 노드 응답 없음 | cordon, drain, 교체·재부팅 | 레플리카가 몰린 서비스·단일 장애점 중단 | **메인 시나리오**: CPU 고갈 → `check_top_process`(A), `restart_service`(B), `reboot_host`(C) |
| 워크로드 | Pod 반복 재시작, 메모리 초과 강제 종료, 배치 실패, 오토스케일링 오작동 | 재시작, 한도 상향, 레플리카·임계값 조정 | 노드 전체 메모리 부족, 다른 서비스 자원 잠식 | 쿠버네티스 없음 → 제외. 메모리는 `fallback_plans.mem`만 |
| 배포·설정 | 배포 직후 오류율 급증, 설정 오류 | 이전 버전·설정 복원 | DB 스키마 호환, 같은 설정을 참조하는 서비스 | 제외 |
| 서비스 런타임 | 응답 지연, 의존 서비스 장애 전파, 인증서 만료 | 스케일 아웃, 트래픽 차단, 인증서 갱신 | DB 커넥션 한도 초과, 정상 기능 중단 | 제외 |

**기존 코파일럿이 약한 영역 중 우리가 노릴 빈틈 (원문) + 금요일 씨앗**
- **상태를 가진 시스템과 연쇄 장애:** 기존 제품은 영향 범위를 모르기 때문에 추천에 그침. 실행 전 영향 계산의 가치가 가장 큼 (DB failover 등은 확장 비전) → 금요일: 해당 없음(단일 PC). L3.
- **처음 보는 장애:** 근거가 부족하면 위험 등급을 올려 사람에게 넘기는 "모르면 멈추는" 설계 → **금요일 씨앗 있음**: 팩에 없는 동작은 C(`default_tier: C`), 근거 없는 수치는 "확인할 수 없음", 분류 불가 트리거의 fallback 계획은 A 단계(확인 명령)만(FR-AG-023). 원안 FR-LT-021.
- **에이전트 기반이 무너진 장애:** API 서버·인증·모니터링 장애 시 조치 불가를 스스로 인지하고 즉시 사람에게 이관 → **금요일 씨앗**: Zabbix·MCP 실패 시 `TOOL_ERROR`/`ZABBIX_UNAVAILABLE`로 표시하고 지어내지 않음, `/api/health`·화면 배너(NFR-AVAIL-004). 원안 FR-LT-022.
- **관측 데이터가 없는 망분리 구간:** 글로벌 SaaS가 들어가기 어려운 국내 환경 → 금요일: LLM 없이 도는 fallback 경로. 장기 폐쇄망 모드(FR-LT-018).

**범위 밖 (원문):** 애플리케이션 코드 버그(원인 지목까지), 데이터 손상, 알람이 안 울리는 업무 오류, 물리 장애, 보안 사고, 외부 클라우드·SaaS 장애(영향 범위 표시까지). → DejaFix도 동일하게 범위 밖.

##### (10) 평가 방법과 지표 — 원문 + 금요일 대응

장애를 직접 주입해 분석 성능과 안전성을 모두 숫자로 증명한다. 장재현 기획서의 "장애 50종 주입"과 차별점 문서의 "안전·위험 조치 시나리오"를 하나의 평가 하네스로 합친다(원문).

| 영역 (원문) | 지표 (원문) | 목표 (원문) | DejaFix 금요일 MVP | 요구사항 |
|---|---|---|---|---|
| 분석 | 감지율, 원인 TOP3 적중률, 영향 범위 정확도, 보고서 정확도 | 적중률 80% 이상 | 리허설 기록표에 감지 여부·TOP3에 정답 포함 여부를 수동 기록(선택) | NFR-EVAL-002 / 이후 003 |
| 안전 | 잘못 통과율(위험한 조치 통과), 과잉 차단율(안전한 조치 차단) | 잘못 통과 0% | 분류 기준 잘못 통과율 "0/N"(안전 회귀 세트, 필수). 과잉 차단율은 같은 세트에 안전 동작(`check_top_process` 등 A, 롤백 있는 B)을 넣어 "C로 잘못 막힌 수"로 함께 출력 | NFR-EVAL-001 |
| 안전 | 영향 예측 정확도 (예측 vs 테스트 클러스터 실제) | 팀에서 기준선 설정 | 없음 | 이후 NFR-EVAL-004 |
| 안전 | 반대 심문 기여도 (있을 때 vs 없을 때 잘못 통과율) | 차이가 클수록 구조 정당성 확보 | 없음 | 이후 NFR-EVAL-004 |
| 안전 | 자동 롤백 성공률 | 팀에서 기준선 설정 | 없음 | 이후 NFR-EVAL-004 |
| 효율 | MTTR, 초동 분석 소요 시간 | 기준선 대비 단축, 초동 30초 | 주입→메일 3분, 분석 60초 상한, 평균 분석 시간 KPI | NFR-PERF-001·003, 이후 NFR-EVAL-007 |

- **시나리오 구성 (원문):** 장애 유형별로 안전한 조치와 위험한 조치를 섞어 총 30~50개 (가능하면 50종) → 금요일: 데모 2개 + 회귀 세트.
- **비교 대상 (원문):** 같은 시나리오에서 K8sGPT·HolmesGPT 같은 오픈소스와 비교 (장재현 기획서 제안). 상용 제품은 공개 자료 기준 비교만 → 이후 NFR-EVAL-005.
- **회귀 평가 (원문):** 모델·프롬프트·온톨로지 변경 시 같은 세트로 재평가 → 금요일: 팩(`actions.yaml`·`prompts/`) 변경 PR마다 안전 회귀 세트 재실행(머지 조건, NFR-MAINT-003에 포함). 이후 NFR-EVAL-006.
- **정답 라벨 (원문):** 주입한 장애는 원인을 알고 있으므로 자동으로 라벨 확보 → 금요일 CPU 주입도 동일.

##### (11) MVP 범위와 환경 — 원문(6명/40일) + 금요일(6명/약 2.5일)

6명 / 40일 기준, 장애 유형 3~4개의 7단계 end-to-end와 안전 레이어, 평가 하네스를 완성하는 것이 목표다(원문). DejaFix는 멘토 지시로 **금요일(10/16) MVP**가 먼저이고, 아래 원문 MVP는 장기 로드맵(L2~L3)의 목표로 읽는다(충돌 #1).

| 구분 | 내용 (원문, 40일 MVP) | DejaFix 금요일 MVP (2-4) |
|---|---|---|
| 필수 코어 | 장애 유형 3~4개의 7단계 end-to-end | CPU 1개(디스크 선택)의 1·2·7단계 end-to-end + 미리보기 계획 |
| 차별 핵심 | 실행 전 영향 시뮬레이션 + 롤백 플랜, 안전 심사 오케스트레이션, 평가 하네스 | 씨앗: 단계별 롤백·위험 표시, 규칙 티어, 안전 회귀 세트 |
| 가볍게 추가 | 허용 목록 기반 정책 엔진 (L1/L2), 사후 검증 | 허용 목록(`actions.yaml`·Zabbix 메서드 허용 목록) — L1까지 |
| 제외 | 웹 터미널, 동시 접속 락, Web Push, PDF 내보내기, 폐쇄망 모드 | 동일 + 조치 실행·승인·JIRA·RAG |

**MVP 시나리오 (원문, 쿠버네티스 기준) + DejaFix 대응 시나리오 (Windows 학원 PC 기준)**

| 장애 유형 (원문) | 안전한 조치 (원문) | 위험한 조치 — 막아야 함 (원문) | DejaFix 대응 (금요일) |
|---|---|---|---|
| 노드 디스크 부족 | 오래된 로그 정리 | 사용 중인 이미지까지 일괄 삭제 | 디스크(선택): `clean_temp_files` B(롤백 필수) / `delete_recursive` C |
| 노드 메모리 압박 | 레플리카가 분산된 상태에서 cordon | 결제 서비스 레플리카 2개 중 1개가 이 노드에 있고 여유 용량 부족한 상태의 drain | 메모리: `fallback_plans.mem`(시연 안 함) |
| 배포 후 오류율 급증 | 무상태 서비스 롤백 | DB 스키마가 바뀐 버전의 롤백 | 해당 없음 |
| 메모리 초과 강제 종료 | 노드 여유가 충분할 때 한도 상향 | 상향 시 노드 전체 메모리 초과 | 해당 없음 |
| (v1.2 추가) CPU 과부하 — **금요일 메인** | `check_top_process`(A), `restart_service`(B, 롤백 있음) | `reboot_host`(C) — LLM이 A라 적어도 코드가 C | D-MAIN·D-BLOCK(11-5) |

**환경 (원문) + 금요일**
- kind/minikube 쿠버네티스 + Prometheus, 카오스 도구(Chaos Mesh/LitmusChaos)로 장애 주입 → 금요일: Zabbix(Ubuntu VM) + Zabbix agent 2(학원 PC) + PowerShell 주입 스크립트(충돌 #2·#18)
- JIRA는 개발자용 무료 인스턴스 또는 목(mock) → 금요일 제외
- 온톨로지는 자원 수십 개 규모로 적재, 가능하면 쿠버네티스 API 기반 자동 적재 → 금요일 제외
- 실제 명령 실행 시연은 반드시 테스트 클러스터에서만 → 금요일은 실행 자체가 없음(장기에도 이 원칙 유지)

##### (12) 리스크와 결정 사항 — 원문 + 금요일

가장 큰 리스크는 "이미 있는 기술인데 왜 만들었나"라는 질문이고, 답은 실측 수치로만 가능하다(원문).

| 리스크 (원문) | 대응 (원문) | 금요일 데모에서의 답 |
|---|---|---|
| "왜 만들었나" 질문 | ① 구체적 빈틈(기존 승인은 정적 규칙, 실행 전 영향 미계산) ② 실제 피해(에이전트 월권, 대형 장애 사례) ③ 실측 수치(잘못 통과율·과잉 차단율)로 답변 | ① 축 ①(공통 엔진·팩) ② AWS S3 2017·Facebook 2021 사례 ③ 금요일 수치: "잘못 통과 0/N, 과잉 차단 M/N, 주입→메일 X분 Y초(리허설 실측)" |
| 경쟁 제품이 비슷한 기능을 정식 출시 | 차별점을 기능이 아니라 검증 방법론에 둠 | 근거 추적·"확인할 수 없음"·회귀 세트 = 방법론의 씨앗 |
| 쿠버네티스·인프라 역량 | 팀에 최소 1~2명 필요 | 금요일은 Zabbix로 대체(이재헌·이태윤) |
| 영향 시뮬레이션은 예측일 뿐 | "의사결정 보조"로 표현하고 정확도는 하네스로 실측 | 금요일 화면 문구도 "미리보기 — 실행되지 않음", "사람이 판단" |

| GPU 자원 | 96GB급 GPU 2장 이상 확보 여부에 따라 주 모델 결정 | 금요일 무관(외부 공급자 자리, (TODO: 추후결정 — 후보: A.X 4.0, Motif-3)) |

**Scheduler 역할 확장 근거**: 구조도의 Scheduler는 "하루 한 번 수집"만 적혀 있어 **실시간 알람 수신 경로가 없음**(정리본 미확정 #12). 웹훅은 수신 포트가 필요한데 Scheduler는 "포트 없음", Backend는 공유 저장소 쓰기 불가라 구조도 원칙과 충돌한다. 따라서 **Scheduler의 "정기 수집"에 30초 주기(**[검토 반영]**, v1은 1분) problem.get 폴링을 추가**하는 것이 구조도의 화살표·권한을 하나도 바꾸지 않는 유일한 안이다. [결정]

**분석 시작 트리거**: Scheduler가 Agent를 호출하면 구조도에 없는 화살표가 생긴다. 대신 **Agent 내부 워커가 10초마다 `shared.db`에서 "리포트 없는 신규 장애"를 찾아 분석**한다. Backend의 "다시 분석" 요청은 Backend → Agent API로 들어온다(구조도 화살표 그대로). [결정]

### 3-3. 컨테이너 구성 (docker-compose 초안)

`infra/docker-compose.yml` (Zabbix는 포함하지 않음 — 외부 서비스)

```yaml
name: dejafix
services:
  frontend:
    build: ../frontend
    ports: ["8080:80"]          # 유일한 외부 공개 포트
    depends_on: [backend]
  backend:
    build: { context: .., dockerfile: backend/Dockerfile }   # [v1.3] 루트 컨텍스트(libs/ 포함)
    env_file: ../.env
    volumes: ["dejafix-data:/data"]
    expose: ["8000"]
    depends_on: [agent]
  agent:
    build: { context: .., dockerfile: agent/Dockerfile }   # [v1.3] 루트 컨텍스트(libs/ 포함)
    env_file: ../.env
    volumes: ["dejafix-data:/data"]
    expose: ["8100"]
    depends_on: [mcp-zabbix]
  mcp-zabbix:
    build: { context: .., dockerfile: mcp-zabbix/Dockerfile }   # [v1.3] 루트 컨텍스트(libs/ 포함)
    env_file: ../.env
    expose: ["8200"]
  scheduler:
    build: { context: .., dockerfile: scheduler/Dockerfile }   # [v1.3] 루트 컨텍스트(libs/ 포함)
    env_file: ../.env
    volumes: ["dejafix-data:/data"]
  # mcp-aws: profiles: ["aws"]  # L1에서 활성화
volumes:
  dejafix-data: {}              # 반드시 named volume (아래 주의)
networks:
  default: { name: dejafix-net }
```

- **[B 수정] 빌드 컨텍스트**: Python 서비스(backend, agent, mcp-zabbix, scheduler)는 `libs/zabbix_ro`(uv workspace 멤버)를 import하므로 `build: ../backend`처럼 서비스 폴더를 컨텍스트로 잡으면 이미지 안에 `libs/`가 없어 빌드가 깨진다. 아래처럼 **컨텍스트는 저장소 루트, Dockerfile만 서비스별**로 지정한다 (frontend는 기존대로).

```yaml
  backend:
    build: { context: .., dockerfile: backend/Dockerfile }
  # agent / mcp-zabbix / scheduler 도 같은 형식
```

- **[B 수정] 데모용 재시작 정책**: Python 4개 서비스에 `restart: unless-stopped`를 붙인다(야간·데모 중 한 번 죽어도 자동 복구). Docker Desktop은 "Start Docker Desktop when you sign in"을 켠다.
- **주의 (SQLite + Windows)**: Windows 폴더 바인드 마운트(`C:\...:/data`)에서는 SQLite WAL 잠금이 불안정할 수 있다. 반드시 **named volume**(WSL2 내부 ext4)을 쓴다. 파일을 들여다볼 때는 `docker compose exec backend sqlite3 /data/shared.db`.
- 개발 중에는 각 서비스를 로컬(`uv run`, `npm run dev`)로 띄워도 되며, 이때 Vite dev 서버(5173)가 `/api`를 `localhost:8000`으로 프록시한다.
- 헬스체크: 모든 HTTP 서비스는 `GET /healthz`. Backend의 `GET /api/health`가 Zabbix·Agent·MCP·DB 상태를 모아 화면 상단에 표시.

### 4-5. Agent 상태 머신 (분석 run)

```
QUEUED → COLLECTING → ANALYZING → VALIDATING → REPORTED → PLANNING → DONE
                 ╲          ╲            ╲                     ╲
                  └──────────┴────────────┴── FAILED(사유) ──────┘ (FALLBACK 리포트 저장)
```

| 상태 | 하는 일 |
|---|---|
| COLLECTING | **고정 수집 세트**를 코드가 먼저 호출(LLM 판단 없이): 장애 상세, 호스트, 관련 아이템 최신값, 최근 1시간 이력, 같은 트리거 최근 7일 발생 횟수, 유지보수 여부. 결과는 모두 `tool_calls`에 근거 ID로 저장 |
| ANALYZING | LLM에 수집 결과 + 스키마 전달. LLM은 필요하면 추가 도구 호출(남은 예산 안) 후 **JSON 스키마로만** 답 |
| VALIDATING | 코드 검증: ① JSON 스키마 통과 ② 모든 수치·사실 항목에 `evidence_ids`가 있고 실제 `tool_calls`에 존재 ③ 근거 없는 수치는 `null` + `unknown_reason`으로 치환 ④ 원인 후보 3개 초과 시 자름 |
| PLANNING | 원인 후보별 조치 단계 생성 → `actions.yaml` 매칭으로 티어 지정(목록에 없으면 C) |

- 프레임워크 없이 Python 코드 상태 머신 + OpenAI 호환 도구 호출(#세팅·Graphio 결정 유지).

- **[검토 반영]** **LLM 동작 모드** (00_팀결정 ②: OpenRouter 보류): ① `LLM_FAKE=true` → 가짜 LLM(고정 JSON, `agent_runs.model='fake'`, 테스트·개발 전용, **데모 금지**) ② `LLM_API_KEY`·`LLM_BASE_URL` 중 빈 값이 있으면 LLM을 부르지 않고 fallback 리포트 + **fallback 계획** ③ 둘 다 설정 → 실 LLM 1회 호출(`max_tokens` 2000 상수). 공급자가 정해지기 전 데모 기본은 ②.
- **[검토 반영]** **fallback 계획**: 트리거 아이템 key를 `metrics.yaml` 별칭(cpu/mem/disk)으로 분류하고 `actions.yaml`의 `fallback_plans.<유형>` 동작 목록으로 계획을 만든다(SAFE-06·07 동일, 분류 불가면 A 단계만. **[v1.3]** `metrics.yaml`에는 있지만 `fallback_plans`에 목록이 없는 유형(`net` 등)도 A 단계만). 공급자 보류 상태에서 M4 계획 미리보기를 시연할 유일한 경로다(요구사항 FR-AG-023).
- **[검토 반영]** **run 상태 규칙**: `agent_runs.status`에 `reported` 포함. LLM 미설정·실패·타임아웃은 FAILED가 아니라 fallback 경로로 계속해 `done` + `error`에 사유(`LLM_NOT_CONFIGURED`/`LLM_TIMEOUT`/`LLM_ERROR`/`LLM_BUDGET`). - **[검토 반영]** **채팅 필수 범위**: 맥락(장애·최신 리포트) + LLM 1회 응답, LLM 미설정 시 규칙 기반 답변(수집 안 된 질문은 "확인할 수 없음 · NOT_COLLECTED"). LLM이 도구를 골라 부르는 루프는 [선택] — 위 "도구 호출 루프는 채팅에서 먼저 완성"은 공급자 확정 후로 미룬다.

## 5. 데이터 설계

### 5-1. 쓰기/읽기 권한 충돌 해결안 (정리본 충돌 #8 = 과제 지시의 "충돌 #4")

**문제**: 구조도는 "공유 저장소 쓰기 = Agent·Scheduler, Backend는 읽기 전용"인데, Backend는 로그인 사용자·메일 기록·대화를 저장해야 한다는 문서가 있다.

**[결정] SQLite 파일 2개 + 테이블별 단일 작성자 원칙**

| 파일 | 의미 | 작성자 | 읽기 |
|---|---|---|---|
| `/data/shared.db` | 구조도의 **공유 데이터 저장소** | Agent, Scheduler (테이블별로 한 명만) | Backend(읽기 전용), Agent, Scheduler |
| `/data/backend.db` | **Backend 전용 저장소** (구조도에 없는 Backend 내부 상태) | Backend만 | Backend만 |

- 대화 저장 주체는 **Agent**로 확정: 대화는 구조도에 "공유 저장소: 수집 지표·대화·변경 계획"으로 명시되어 있고, 사이트·Claude·타 에이전트가 같은 Agent를 쓰므로 대화 기록도 Agent 쪽에 있어야 일원화된다. Backend는 사용자 메시지를 Agent로 넘기기만 하고, 기록 조회는 `shared.db`를 읽는다. (백엔드 가이드의 "Backend가 SQLite에 대화 저장"은 정정)
- 사용자가 계획을 "검토 완료/폐기"하는 상태 변화는 Backend 쓰기가 필요하므로 `shared.db`가 아닌 `backend.db.plan_reviews`에 둔다. 계획 자체(내용)는 Agent 소유로 불변.
- Backend는 `sqlite3.connect("file:/data/backend.db", uri=True)` 후 `ATTACH 'file:/data/shared.db?mode=ro' AS shared`로 두 파일을 JOIN한다. 읽기 전용이 **연결 수준에서 강제**됨.
- 모든 연결: `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000; PRAGMA foreign_keys=ON;`
- 다른 파일 간 참조(예: `conversations.user_id` → `backend.db.users.id`)는 FK 없이 값만 저장.
- 스키마 생성·변경: `shared.db`는 Agent가 기동 시 마이그레이션(Scheduler 테이블 포함, 단일 소유자), `backend.db`는 Backend가 마이그레이션. 원본 SQL은 `contracts/db-schema.sql`.
- **[B 수정] 기동 순서 문제**: Scheduler가 Agent보다 먼저 뜨면 `incidents` 테이블이 없어 첫 폴링이 실패한다(compose `depends_on`은 "시작"만 보장). 그래서 **스키마 적용은 "모든 문장이 `CREATE TABLE IF NOT EXISTS`인 `contracts/db-schema.sql`을 Agent·Scheduler 둘 다 기동 시 실행"** 으로 바꾼다(멱등). 테이블별 **쓰기** 소유자 규칙은 그대로. MVP 기간에는 `ALTER`를 하지 않고, 스키마가 바뀌면 개발 DB를 지우고 다시 만든다(데모 직전 데이터는 11-3 백업).
- **[B 수정] 읽기 전용 ATTACH 주의**: WAL 모드 DB를 `mode=ro`로 열려면 `-wal`/`-shm` 파일이 이미 있거나 디렉터리가 쓰기 가능해야 한다. 같은 named volume을 쓰므로 문제없지만, Backend가 Agent보다 먼저 떠서 `shared.db`가 아직 없으면 ATTACH가 실패한다 → Backend는 `shared.db`가 없으면 `/api/health`에 `shared_db: "waiting"`을 내고 요청마다 재시도한다.

| 테이블 | 파일 | 단일 작성자 |
|---|---|---|
| incidents, hosts_snapshot, metrics_daily, scheduler_jobs | shared | Scheduler |
| agent_runs, tool_calls, analysis_reports, change_plans, plan_steps, conversations, messages | shared | Agent |
| users, notification_recipients, mail_logs, plan_reviews, audit_logs | backend | Backend |

### 5-2. `shared.db` DDL 초안

> **[v1.3]** 5-1 [B 수정]·DR-016의 "모든 문장 멱등" 규칙에 맞춰 5-2·5-3의 모든 `CREATE TABLE`/`CREATE INDEX`를 `IF NOT EXISTS`로 바꿨다(v1.2 초안은 빠져 있어 두 번째 기동부터 실패).

```sql
-- ===== Scheduler 소유 =====
CREATE TABLE IF NOT EXISTS incidents (
  id               INTEGER PRIMARY KEY,
  zabbix_eventid   TEXT NOT NULL UNIQUE,
  zabbix_triggerid TEXT NOT NULL,
  hostid           TEXT,
  host_name        TEXT,
  title            TEXT NOT NULL,            -- problem.name
  severity         INTEGER NOT NULL,         -- 0~5 (Zabbix 기준)
  status           TEXT NOT NULL CHECK (status IN ('problem','resolved')),
  started_at       TEXT NOT NULL,            -- problem.clock (UTC ISO)
  resolved_at      TEXT,                     -- r_clock
  acknowledged     INTEGER NOT NULL DEFAULT 0,
  tags_json        TEXT NOT NULL DEFAULT '[]',
  first_seen_at    TEXT NOT NULL,            -- DejaFix가 처음 본 시각
  last_seen_at     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_incidents_status ON incidents(status, severity);

CREATE TABLE IF NOT EXISTS hosts_snapshot (               -- 매일 03:00 서버 사양
  hostid        TEXT NOT NULL,
  snapshot_date TEXT NOT NULL,              -- YYYY-MM-DD
  host          TEXT NOT NULL,
  name          TEXT,
  available     TEXT,                       -- 확인 불가면 NULL
  os            TEXT,
  cpu_cores     INTEGER,
  memory_bytes  INTEGER,
  disk_json     TEXT,                       -- [{fs, total_bytes}]
  groups_json   TEXT,
  collected_at  TEXT NOT NULL,
  PRIMARY KEY (hostid, snapshot_date)
);

CREATE TABLE IF NOT EXISTS metrics_daily (                -- 매일 03:00 전일 요약 (trend.get)
  hostid      TEXT NOT NULL,
  item_key    TEXT NOT NULL,                -- system.cpu.util, vm.memory.util, vfs.fs.size[C:,pused] ...
  day         TEXT NOT NULL,
  v_min REAL, v_avg REAL, v_max REAL,
  units       TEXT,
  samples     INTEGER,
  collected_at TEXT NOT NULL,
  PRIMARY KEY (hostid, item_key, day)
);

CREATE TABLE IF NOT EXISTS scheduler_jobs (
  job          TEXT PRIMARY KEY,            -- poll_problems | daily_collect | retention ([검토 반영] poll_problems 행만 [필수])
  last_run_at  TEXT, last_ok_at TEXT,
  status       TEXT, message TEXT
);

-- ===== Agent 소유 =====
CREATE TABLE IF NOT EXISTS agent_runs (
  id              TEXT PRIMARY KEY,         -- uuid
  kind            TEXT NOT NULL CHECK (kind IN ('analyze','plan','chat')),
  incident_id     INTEGER REFERENCES incidents(id),
  conversation_id TEXT,
  caller          TEXT NOT NULL,            -- worker | backend | claude | agent:<name>
  requested_by    INTEGER,                  -- backend.db users.id (FK 없음)
  status          TEXT NOT NULL,            -- queued|collecting|analyzing|validating|reported|planning|done|failed ([검토 반영] reported 추가)
  model           TEXT,
  tool_call_count INTEGER DEFAULT 0,
  tokens_in INTEGER, tokens_out INTEGER, cost_usd REAL,
  error           TEXT,
  started_at      TEXT NOT NULL, finished_at TEXT
);

CREATE TABLE IF NOT EXISTS tool_calls (                   -- = 근거(Evidence)
  id             TEXT PRIMARY KEY,          -- 'ev_' + 짧은 id, 리포트에서 참조
  run_id         TEXT NOT NULL REFERENCES agent_runs(id),
  seq            INTEGER NOT NULL,
  tool           TEXT NOT NULL,             -- zabbix_get_history ...
  args_json      TEXT NOT NULL,
  ok             INTEGER NOT NULL,
  duration_ms    INTEGER,
  result_summary TEXT,                      -- 화면 표시용 한 줄
  result_json    TEXT,                      -- 최대 32KB로 잘라 저장
  data_clock     TEXT,                      -- 결과 데이터의 수집 시각(가장 최근 값 기준)
  called_at      TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS analysis_reports (
  id             INTEGER PRIMARY KEY,
  incident_id    INTEGER NOT NULL REFERENCES incidents(id),
  run_id         TEXT NOT NULL REFERENCES agent_runs(id),
  version        INTEGER NOT NULL,          -- 다시 분석하면 +1
  kind           TEXT NOT NULL CHECK (kind IN ('llm','fallback')),
  summary        TEXT NOT NULL,
  impact_json    TEXT NOT NULL,             -- {hosts:[], services:[], user_impact, evidence_ids}
  causes_json    TEXT NOT NULL,             -- 아래 형식
  facts_json     TEXT NOT NULL,             -- [{label, value|null, unit, unknown_reason, evidence_ids, collected_at}]
  unknowns_json  TEXT NOT NULL,             -- ["확인할 수 없음" 항목과 사유]
  next_checks_json TEXT NOT NULL,           -- 사람이 확인할 것 (읽기 전용 확인)
  created_at     TEXT NOT NULL,
  UNIQUE (incident_id, version)
);
-- causes_json 예: [{"rank":1,"title":"백업 작업으로 디스크 사용 급증","confidence":"medium",
--   "reasoning":"...","evidence_ids":["ev_a1","ev_a3"],"verify":"df 결과로 용량 재확인"}]
-- confidence는 low/medium/high 3단계만 (가짜 정밀도 방지, 퍼센트 금지)

CREATE TABLE IF NOT EXISTS change_plans (
  id           INTEGER PRIMARY KEY,
  incident_id  INTEGER REFERENCES incidents(id),
  report_id    INTEGER REFERENCES analysis_reports(id),
  run_id       TEXT NOT NULL REFERENCES agent_runs(id),
  title        TEXT NOT NULL,
  goal         TEXT,
  mode         TEXT NOT NULL DEFAULT 'preview' CHECK (mode = 'preview'),  -- 실행 모드 자체가 없음
  max_tier     TEXT NOT NULL CHECK (max_tier IN ('A','B','C')),
  assumptions_json TEXT NOT NULL DEFAULT '[]',
  created_at   TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS plan_steps (
  id            INTEGER PRIMARY KEY,
  plan_id       INTEGER NOT NULL REFERENCES change_plans(id),
  seq           INTEGER NOT NULL,
  action_id     TEXT,                       -- packs/it/actions.yaml의 id, 없으면 NULL
  title         TEXT NOT NULL,
  target        TEXT,                       -- 대상 호스트/경로
  command_preview TEXT,                     -- 보여주기만 하는 명령 예시
  tier          TEXT NOT NULL CHECK (tier IN ('A','B','C')),
  rationale     TEXT,
  precheck      TEXT,                       -- 실행 전 확인할 것
  expected_effect TEXT,
  risk          TEXT,
  rollback      TEXT,                       -- B 티어는 필수 (검증에서 강제)
  evidence_ids_json TEXT NOT NULL DEFAULT '[]',
  UNIQUE (plan_id, seq)
);

CREATE TABLE IF NOT EXISTS conversations (
  id          TEXT PRIMARY KEY,             -- uuid
  user_id     INTEGER,                      -- backend.db users.id
  caller      TEXT NOT NULL DEFAULT 'backend',
  incident_id INTEGER REFERENCES incidents(id),
  title       TEXT,
  created_at  TEXT NOT NULL, updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS messages (
  id              INTEGER PRIMARY KEY,
  conversation_id TEXT NOT NULL REFERENCES conversations(id),
  role            TEXT NOT NULL CHECK (role IN ('user','assistant')),
  content         TEXT NOT NULL,
  run_id          TEXT REFERENCES agent_runs(id),   -- assistant 메시지의 근거 연결
  created_at      TEXT NOT NULL
);
```

### 6-3. 3티어 정책과의 관계

| 티어 | 장기 정의 (통합·Graphio) | **MVP에서의 의미** | 화면 표시 |
|---|---|---|---|
| A · 조회 | 승인 없이 실행 (df, journalctl, kubectl get) | **Agent가 MCP 도구로 직접 하는 조회만 실제로 수행**. 계획에 들어간 A 단계(셸 조회 명령)는 "사람이 확인할 명령"으로 **표시만** | 초록 배지 "조회 · 안전" |
| B · 가역 변경 | 건별 승인 후 실행 (로그·임시 파일 정리, 서비스 재시작 일부) | **미리보기만**. 사전 확인·롤백 필수. "장기에는 승인 후 실행 대상" 문구 | 주황 배지 "변경 · 승인 필요(미구현)" |
| C · 차단 | 실행 불가 (rm -rf, 재부팅, drain) | **미리보기에도 경고와 함께만** 표시, 대안 단계 제시 권장 | 빨강 배지 "금지 · 사람이 판단" |

- 즉 MVP는 "3티어 정책을 **분류·표시 체계**로만 먼저 도입"하고, 실행 엔진은 L3에서 붙인다. `actions.yaml`이 장기 실행 허용 목록의 원본이 되므로 지금 만든 분류가 그대로 재사용된다.
- `packs/it/actions.yaml` 초안 형식:

```yaml
version: 1
actions:
  - id: check_disk_usage
    title: 디스크 사용량 확인
    tier: A
    command_preview: { windows: "Get-PSDrive C", linux: "df -h" }
  - id: clean_temp_files
    title: 임시 파일 정리
    tier: B
    requires: [precheck, rollback]
    # [v1.3] B 동작은 precheck·rollback 문구가 없으면 SAFE-07로 C 강등된다 → fallback 계획에 쓰는 B 동작은 아래처럼 문구를 반드시 둔다(명령은 예시, 담당자 확인)
    # 되돌릴 수 있게 "삭제" 대신 "격리 폴더로 이동"으로 미리보기한다(v1.2의 cleanmgr는 되돌릴 수 없어 B 정의와 맞지 않음)
    command_preview: { windows: 'Move-Item $env:TEMP\* (Join-Path $env:TEMP ..\dejafix-quarantine)', linux: 'find /tmp -mtime +7 -exec mv {} /var/tmp/dejafix-quarantine/ \;' }   # Windows 경로는 작은따옴표(큰따옴표 안의 \ 는 이스케이프로 읽힘)
    precheck: "임시 폴더 크기와 사용 중인 파일 확인 (Get-ChildItem $env:TEMP -Recurse | Measure-Object Length -Sum)"
    rollback: "격리 폴더의 파일을 원래 위치로 다시 이동 (Move-Item)"
  - id: restart_service
    title: 서비스 재시작
    tier: B
    requires: [precheck, rollback]
    command_preview: { windows: "Restart-Service -Name <서비스 이름>", linux: "systemctl restart <서비스>" }
    precheck: "부하 상위 프로세스가 해당 서비스인지, 서비스 상태 확인 (Get-Service -Name <서비스 이름>)"
    rollback: "서비스가 다시 뜨지 않으면 시작 (Start-Service -Name <서비스 이름>)"
  - id: check_top_process          # [검토 반영] fallback 계획용
    title: 부하 상위 프로세스 확인
    tier: A
    command_preview: { windows: "Get-Process | Sort-Object CPU -Descending | Select-Object -First 10", linux: "top -b -n1 | head -20" }
  - id: reboot_host
    title: 서버 재부팅
    tier: C
  - id: delete_recursive
    title: 디렉터리 강제 삭제
    tier: C
default_tier: C
# [검토 반영] LLM 없이 만드는 fallback 계획(4-5). 키는 metrics.yaml 별칭.
# fallback에 쓰는 B 동작(restart_service, clean_temp_files)은 precheck·rollback 문구를 yaml에 함께 둔다(SAFE-07).
fallback_plans:
  cpu:  [check_top_process, restart_service]
  mem:  [check_top_process, restart_service]
  disk: [check_disk_usage, clean_temp_files]
```

### 7-2. Backend ↔ Agent 인터페이스 (`contracts/agent-api.md`)

- 호출자 구분 `caller`: `backend` | `claude` | `agent:<name>` → `agent_runs.caller`에 기록(구조도 "사이트·Claude·타 에이전트 공통 호출" 대비).

### 7-3. Agent ↔ Zabbix MCP 도구 목록 (`contracts/mcp-tools.md`)

- 전송: MCP streamable HTTP, `http://mcp-zabbix:8200/mcp`, 헤더 `X-Internal-Token`.

- **크리티컬 패스 = C → E → F → G → H.** 여기에 걸린 사람(이재헌·이태윤·노예진)은 다른 일을 받지 않는다.
- **[검토 반영]** LLM 공급자는 보류(00_팀결정 ②)라 크리티컬 패스에서 뺀다. G는 "Agent ↔ 실 MCP ↔ (공급자 확정 시 실 LLM, 아니면 fallback 리포트+계획)"으로 통과 판정한다.
- 크리티컬 패스 밖에서 막히는 일은 전부 목으로 우회한다(3-5 로컬 대체, `MAIL_PROVIDER=console`, 가짜 LLM).

### 11-3. DB 백업

- SQLite WAL 모드에서는 파일 복사가 안전하지 않으므로 **SQLite 백업 API**를 쓴다 (`infra/scripts/backup-db.ps1`, 담당 노예진).

```powershell
$ts = Get-Date -Format yyyyMMdd-HHmm
docker compose -f infra/docker-compose.yml exec agent python -c "import sqlite3;[sqlite3.connect(f'/data/{n}.db').backup(sqlite3.connect(f'/data/bak-{n}.db')) for n in ('shared','backend')]"
docker compose -f infra/docker-compose.yml cp agent:/data/bak-shared.db  backups/shared-$ts.db
docker compose -f infra/docker-compose.yml cp agent:/data/bak-backend.db backups/backend-$ts.db
```

- 시점: 매일 09:00 / 스키마 변경 전 / 리허설 직전 / 10/16 11:30 **골든 백업**(시드 계정 + 깨끗한 상태 — 데모 직전 이 상태로 되돌릴 수 있게).
- 보관: `backups/`(git 제외) 최근 5개. 복원: `docker compose stop` → `docker compose cp`로 `/data/`에 덮어쓰기 → `start`.

### 13-4. 브랜치·커밋·PR 규칙

- **[v1.3] 브랜치 전략 = 간소화 Git Flow (확정)**
  - `main`: 배포·데모 안정본. 직접 push 금지. dev → main 머지는 데모·배포 시점에만(팀장 승인).
  - `dev`: 개발 통합 브랜치. **GitHub 기본 브랜치를 dev로 설정**해 PR이 자동으로 dev를 향하게 한다. 직접 push 금지, PR + 승인 1명 이상, squash 머지.
  - 작업 브랜치(`feat/` `fix/` `docs/` `night/`)는 dev에서 따고 dev로 PR.
  - release·hotfix 브랜치는 쓰지 않는다(6명·7주 규모에 관리 부담만 늘어남). 데모 버전은 main에 태그로 남긴다.
  - 이유: 배포 서버가 없어 GitHub Flow의 "머지 = 배포" 이점이 없고, 야간 루프가 밤새 PR을 만들므로 dev를 통합·검증 버퍼로 두고 안정 시점에만 main으로 올린다.
- 브랜치 이름: `feat/<영역>-<주제>`, `fix/<영역>-<주제>`, `docs/<주제>`, `night/<파트>-<MMDD>`(야간 루프 전용), `release/demo-1016`(데모 동결 — [v1.3] 브랜치가 아니라 main 태그). 영역 = `frontend|backend|agent|mcp|scheduler|libs|infra|contracts|docs`.

### 13-6. Windows 학원 PC 주의점

1. **줄바꿈**: 루트 `.gitattributes`에 `* text=auto eol=lf`, `*.ps1 text eol=crlf`. 컨테이너 안에서 도는 `.sh`가 CRLF면 실행이 깨진다. `git config --global core.autocrlf false` 권장.
2. **긴 경로**: `git config --global core.longpaths true` (node_modules).
3. **PowerShell 실행 정책**: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` (스크립트 실행용).
4. **SQLite**: 컨테이너에서는 named volume만(3-3). 로컬 실행 시에는 Windows 경로의 `.db` 파일을 한 프로세스씩만 쓰는 것을 전제로 하고, 컨테이너와 로컬 프로세스가 같은 파일을 동시에 열지 않는다.
5. **WSL2 메모리**: 8GB 이하 PC는 `%UserProfile%\.wslconfig`에 `memory=4GB` 정도로 제한(VM과 동시 실행 시 메모리 부족 방지 — VM 호스트 PC는 VM 4GB + Docker 4GB 이상 필요, 부족하면 compose는 다른 PC에서).
6. **방화벽**: 처음 서버를 띄울 때 뜨는 허용 창에서 "개인/도메인" 허용. 데모 호스트 PC 8080, VM 호스트 PC 8081·10051 인바운드.
7. **포트 충돌**: 8080·8000이 이미 쓰이면 compose의 호스트 포트만 바꾸고 `.env` `APP_BASE_URL`을 맞춘다.
8. **시간대**: 컨테이너·DB는 UTC, 화면만 KST(3-6). Windows 시계가 틀리면 SAFE-09 "오래된 값" 판정이 틀어지므로 시간 동기화 켜기.
9. **백신 실시간 검사**가 `node_modules`·`.venv`를 느리게 하면 해당 폴더 예외 등록 [선택].
